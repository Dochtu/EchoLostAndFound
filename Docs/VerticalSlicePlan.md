# 第一章垂直切片开发路线

阶段 3 设计稿，2026-11-21。唯一写入：Game Director。**以下均为未来实施规划，不是本轮代码/资源制作授权。** 阶段 3 以用户本轮确认的既有 GDD、StoryBible 为已验收设计输入；不修改其历史验收记录。

## 1. 产品目标与切片边界

优先级依本轮任务：画面质量 → 沉浸与人物 → 玩法完整 → AI 交互 → 可维护扩展。切片必须把漂亮的场景、可检查的物件、有表演的两位人物和可核验的调查闭环一起交付，不能以功能按钮齐全替代第一人称体验。

切片内容：失物招领处 ↔ 候车大厅 ↔ 站台安全内侧；老周与林遥；E01–E05、D01–D03、R01/R02、A01 与 A02 两种保管选择；中文自由输入和固定案务；手册、近检、关系反馈、存档、雨夜音画和 Windows 构建。许澄及后章关键内容不纳入本次制作验收；可以保留未开封磁带/车票的章间引入，不制作第二章调查。

切片结束条件仍为 E01 已入档且 A02 已完成，R01/R02 不强制完成。完整产品规则会开放第二章；独立第一章包把这一开放标记保存，显示“第一章调查交接”并提供返回补证/读取/退出，不伪造一个终局 END，不因未实现第二章而封死第一章回访。进入第二章的实际内容属于后续授权。

剧情规则和接口源分别是 [StoryBible](StoryBible.md)、[第一章映射](Chapter01ImplementationMap.md)和 [DataSchema](DataSchema.md)。客户端、部署、视觉、测试依次见 [TechnicalDesign](TechnicalDesign.md)、[Architecture](Architecture.md)、[VisualDirection](VisualDirection.md)、[TestPlan](TestPlan.md)。本轮审查见 [阶段报告](Stage3TechnicalDesignReview.md)。

编号是交付标签，不表示必须先做完 M4 才能开始 M5。M5 可在契约冻结后与 M1–M4 并行；M4 资产准备与 M2 控制并行；美术样段在 M1 即开始，在 M8 整体收敛。M6 可用固定/mock 模型验证接口，真实供应商未批准不阻塞主线。M3/M4 的表现原型可用契约桩，但验收时必须接 M5 的唯一权威规则；不能形成客户端和后端各判一遍的双份真相。

四个并发名额含 Director，最多三个专业任务同时工作。每次开工由 Director 给出准确文件清单，接受者确认后独占；完成、停止编辑并移交后方可更换作者。场景始终由 Unity Engineer 单独集成，Art Director 提交资源及摆放/灯光要求，不同时编辑场景。

## 3. 后续文件分配原则

本表是未来允许范围及设计落点，不是自动文件锁或本轮写入授权；新增文件须在对应里程碑开工单中从此范围列成准确名单。所有 Assets 下文件包含相应 .meta；不要为重命名重新生成 GUID。

| 作者 | 未来范围 | 互斥与跨模块界限 |
| --- | --- | --- |
| Unity Engineer | Assets/_Project/Scripts/{Core,Player,Interaction,NPC,Dialogue,Evidence,Investigation,Save,AI,UI}/；Scenes/{Bootstrap,MainMenu,Station}/；Prefabs/{Player,NPCs,Interactables,UI}/ | 独写 Scene、Prefab、运行时 C#；不能写 QA 测试或擅改 HDRP 公共配置 |
| Art Director | Assets/_Project/Art/{Environment,Characters,Props,Textures,Materials}/、VFX/、Audio/ | 模型/材质/纹理/动画原件在其目录；人物 Prefab 和 Scene 交 Unity 集成 |
| Narrative Designer | Assets/_Project/Data/{Evidence,NPCs,Chapters}/ | 只把获批文本/条件转为数据，不在转换时编新真相；服务端内容副本由 AI 按相同版本打包验证 |
| AI Engineer | Server/app/、Server/requirements.txt 及后续明确分配的打包文件 | 不写 Server/tests/；依赖安装/版本锁须先获授权；不生成客户端密钥 |
| QA Engineer | Assets/_Project/Tests/、Server/tests/ | 测试资产与配置由 QA 独写，失败修复回业务作者；不为通过降低断言 |
| Director | 本轮八份设计稿的协调；后续具体获准的根文档/版本管理文件 | GDD/StoryBible/来源保持不动；Packages/ProjectSettings/共享 HDRP、Git/LFS 改动须单独明确授权 |

未来文档里的 C#、Python、Scene 和资源路径均为设计目标，以 TechnicalDesign 的模块拆分为准，本轮没有创建这些文件。

## 4. M0–M10 实施与验收

工作量使用相对复杂度点 1/2/3/5/8 表示，不是人日或工期承诺。需等工具、资产许可和目标机确定、首个样段测量后重估；点数不可机械相加推算完成日期。每个里程碑同时安排 QA 的行为验证，不到 M9 才开始找问题。

## 6. 首次版本管理基线方案

当前 Git 初始化但没有跟踪和提交基线；建议 M0 先只读审核清单，而后为用户列出准确的暂存/提交操作，获得明确授权再执行。开发阶段获准不自动授权 Git 操作。

- 拟保留并纳入基线：正式 Assets 与全部对应 .meta、Packages/manifest.json 和 packages-lock.json、ProjectSettings、Docs（含来源）、Server 源码/依赖声明、README/AGENTS、现有 .codex 角色与工程根配置。字体/第三方资源先核许可证；不因“在 Assets 下”就推定可发行。
- 排除：Unity/Python/IDE 缓存、真实 .env/Key、虚拟环境、构建/录屏/测试产物、本地日志、玩家 SQLite 与备份。运行时数据库推荐在用户目录，不进入工程仓库；若测试 fixture 必须入库，明确其为脱敏合成资料并分配具体路径。
- 现有忽略规则先逐个验证正式资源无误忽略，再检查即将提交文本中是否嵌入凭据；.gitignore 不能识别任意正文中的密钥。未跟踪文件只能通过精确清单与哈希比较保护，不能用 git diff 为空证明没有改动。
- LFS 候选按真实导入清单评估模型/创作源（FBX/BLEND 等）、图层源（PSD 等）、大纹理/高动态范围图（EXR 等）及无损音频（WAV 等），不是承诺把所有这类扩展名都纳入。先测体积/修改频率、远端额度、协作下载与发行权，再提出具体 .gitattributes；不对整个 Assets 使用通配规则，不把文本 Scene/Prefab/.meta 一并交给 LFS。
- 备份和远端推送分开授权。初始本地提交、远端绑定、推送、大文件规则各给独立可审查操作，不重置、清理或删除现有未跟踪资源以制造“干净状态”。
