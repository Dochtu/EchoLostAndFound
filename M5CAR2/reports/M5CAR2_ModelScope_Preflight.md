# M5-C-A-R2 ModelScope 平台部署预检

> 状态声明：本文是**验证方案与判定门槛**，不是平台验证结果。本轮未登录平台、未部署、未调用真实模型、未消耗魔粒、未修改线上创空间。所有“预期/待验证”项均不得在验收中计为通过。

## 1. 已知平台事实（来自 R1 资料与公开说明，需在平台上复核）

| 事实 | 影响 |
| --- | --- |
| 推理 API：`https://api-inference.modelscope.cn/v1`，Bearer 鉴权 | 服务端以环境变量注入 Key，走 OpenAI 兼容 `/chat/completions` |
| 免费 API-Inference 无 SLA | 必须保留 fallback 与熔断，不能把可用性写进验收前提 |
| 计费以“魔粒”计，单次约 0.5 / 1 / 2（随模型与 token 档位） | 首轮 5 次请求的预算可按最坏 2 魔粒/次估 |
| 无官方 token ↔ 魔粒换算 | 只能按平台账单页与实际余额差核对，不能由 token 数反推 |
| 持久化仅 `/mnt/workspace`，迁移/重命名会丢 | 台账与 epoch 哨兵若都放这里，会一起丢 → 预算可回滚 |
| Docker 创空间固定暴露 7860 | `app.server_entry` 默认端口与之一致 |
| 平台保留 `Authorization`、`X-modelscope-*`、`X-studio-*` 等头 | 客户端不能依赖这些头；我方鉴权用 `X-Dialogue-Token` |
| 模型 ID 形如 `owner/name` | `LLM_MODEL` 必须是完整 ID，不能用别名 |

## 2. 场景 A：持久化目录与重启后的预算恢复

**要回答的问题**：重启/重建创空间后，SQLite 台账与 epoch 哨兵是否仍在，`health.ledger.global_used` 是否保持？

**方案**：

1. 在**临时验证空间**（非线上）设置 `LLM_LEDGER_EPOCH_PATH=/mnt/workspace/state/ledger-epoch.json`、`DEFAULT_STATE_DIR=/mnt/workspace/state`，`APP_ENTRY_MODE=mock` 启动。
2. 通过 mock 入口写一次台账（mock 也记账），记录 `GET /api/v1/health` 的 `ledger.global_used`、`epoch_fingerprint`。
3. 平台“重启”服务；再次读取同样字段。
4. 再执行一次“停止 → 启动”（若平台提供重建/迁移，另做一次迁移）。
5. 对照：文件是否仍在、mtime 是否变化、`ledger.status` 是否为 `ok`。

**判定门槛**：

- `global_used` 重启后不减少才算 PASS；
- 若重启即清零或 `ledger` 变 `unavailable`，则 live 不得开启，除非接受“每次重启重置预算”的书面风险；
- 迁移后丢失 → 记录为平台限制，不能靠应用侧修复。

**证据**：两次 health JSON、`ls -l /mnt/workspace/state`、平台重启操作截图/日志、时间戳。

## 3. 场景 B：SQLite 台账与哨兵共同回滚风险

**机制**：预算上限依赖“台账累计用量 + epoch 指纹”。若两者在同一持久盘、且平台快照/回滚把整盘恢复，则台账和哨兵一起回到旧状态，已消耗额度被“复原”，可再次消费。

**方案**：

1. mock 模式记录 `global_used=U0` 与 `epoch_fingerprint=F0`。
2. 消耗若干额度到 `U1`。
3. 复制 `/mnt/workspace/state` 到备份目录（同一磁盘内），再消耗到 `U2`。
4. 停服，用备份覆盖 state，启动，读取 `global_used`。
5. 若回到 `U1` 且服务接受继续消费 → 证明可回滚，记录差额与可重复次数。

**判定门槛**：可回滚即视为**预算完整性缺陷**；在 C 项有结论前，真实模型只允许在“单轮 5 次、人工盯守、事后对账”的方式下使用。

## 4. 场景 C：独立可信预算记录可行性

候选：

| 方案 | 可行性 | 结论 |
| --- | --- | --- |
| 平台账单/控制台余额作为权威 | 只能人工查看，无 API 保证 | 可作事后对账，不能作实时门禁 |
| 外部数据库/对象存储 | 本项目无额外付费资源，平台未提供 | 不可行 |
| 客户端/浏览器记账 | 可伪造，且违背“服务端权威” | 不可行 |
| 仓库内追加式日志 + 人工签名 | 非实时，易漏记 | 仅审计辅助 |
| 平台环境变量/密钥存“已用额度” | 环境变量只读，不能写回 | 不可行 |

**结论**：当前没有独立可信预算记录。可行做法是“平台余额人工对账 + 本地台账 + 首轮 5 次硬上限 + 异常即停”，并在验收中明确这是**残余风险**，不是已解决项。

## 5. 场景 D：平台代理拓扑与 `X-Forwarded-For` 可信范围

**要回答的问题**：请求到达应用时，`X-Forwarded-For` 是平台写入、透传客户端伪造值，还是被剥除？应用看到的直连地址是什么？

**方案**：

1. 只读探针：在验证空间部署一个**仅回显请求头**的最小服务（不接业务、不读密钥），返回 `X-Forwarded-For`、`X-Real-IP`、`Forwarded`、直连 peer、`Host`。
2. 分别用普通请求、带伪造 `X-Forwarded-For: 1.2.3.4` 的请求、以及平台文档声明的入口访问。
3. 记录哪些头被保留/覆盖/删除。
4. 只有在能确定“平台在边缘覆盖 XFF”后，才可设置 `TRUST_FORWARDED_FOR=true` 与具体 `TRUSTED_PROXY_CIDRS`；否则保持 `false`（当前默认）。

**现状**：`TRUSTED_PROXY_CIDRS` 为空、`proxy_headers=false`，限流按代理地址计，**多用户会共享一个桶**；E2E P1 已证明伪造 XFF 不能买到新桶（在不可信模式下）。

**判定门槛**：拿不到平台拓扑结论前，不得开启 XFF 信任；若共享桶影响体验，只能提高限额（需重新评估滥用风险）或等待平台结论。

## 6. 场景 E：服务端 API Key 安全注入

**方案**：

1. 只在平台“环境变量/密钥”处设置 `LLM_API_KEY`（以及 `LLM_BASE_URL`、`LLM_MODEL`），不写入镜像、仓库、`.env.example`、客户端资源。
2. 构建上下文检查：镜像层、`docker history`、容器内 `/proc/1/environ` 仅平台可见；应用日志不得打印 Key。
3. 用 `GET /health` 的 `model_ready` 判断配置是否生效，不返回 Key 本身。
4. 扫描：对镜像文件系统与日志执行与 R2 相同的密钥规则扫描。

**判定门槛**：镜像/日志/响应任一出现 Key 即 FAIL，立即删除并轮换。

## 7. 场景 F：首轮不超过 5 次真实模型请求

前置：A、D 有结论；用户明确授权；余额充足（≥10 魔粒，留余量）；线上空间不在本轮改动范围内（使用临时验证空间）。

**逐次计划**（每次请求前后记录）：

| # | 请求 | 目的 | 记录 |
| --- | --- | --- | --- |
| 1 | `GET /health` | 确认 live、ledger、model_ready | 不耗魔粒 |
| 2 | `POST /sessions`（老周）→ 1 次 `turns` 文本提问 | 最小真实调用 | `turn_id`、`source=external_model`、token 用量、health 台账增量 |
| 3 | 同一会话再 1 次提问 | 验证累计与上限 | 同上 |
| 4 | 新建林遥会话 1 次提问 | 验证会话隔离与预算 | 同上 |
| 5 | 触发超时/失败场景（如临时错误模型名） | 验证 fallback 与熔断，**不重试** | `fallback_reason`、上游调用次数 |

**硬规则**：每次请求间隔人工确认；任一次 `5xx`、超时、`fallback`、台账增量异常即停止，不再发下一次；总计不超过 5 次，不并发。

**记录项**：平台账单余额（前/后）、`ledger.global_used`、`ledger.epoch_fingerprint`、耗时、token 数、响应中的 `provider`/`source`/`is_synthetic`。

## 8. 场景 G：异常即停与回滚 Mock

**停止条件**（任一命中）：

- `health.ledger.status != ok` 或 `global_used` 与预期不符；
- 出现 `external_model` 但平台余额未变化，或余额变化与台账不一致；
- 任意 5xx / 连续超时 / 熔断打开；
- 响应中出现密钥、系统提示或越权内容；
- 发现平台回滚导致额度复原。

**回滚步骤**：

1. 平台“停止”创空间（先停，避免继续消费）。
2. 环境变量改回 `APP_ENTRY_MODE=mock`、`MODEL_PROVIDER=mock`，清空/停用 `LLM_API_KEY` 注入（或轮换）。
3. 启动后核对 `health.ledger` 与 `/api/v1/meta`，确认 `is_synthetic=true`、无外部调用。
4. 代码回退到已验收基线 `4c51712c362e18bfcf9215cea766e61731773c74`（如需）。
5. 保存现场（台账副本、日志、平台操作记录）并上报；**不执行** `ledger_admin reset`，不手工改台账。
6. 在报告中记录实际消耗与差额，不以“已回滚”掩盖已发生的消费。

## 10. 结论

平台真实上线仍被 **A（持久化）** 与 **D（代理拓扑）** 阻塞；C 项确认“无独立可信预算记录”，只能以人工对账 + 5 次硬上限控制风险。以上均需用户授权后才能执行，本轮不产生任何平台侧变更。
